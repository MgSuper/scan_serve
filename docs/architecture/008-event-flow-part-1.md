**Version:** 1.0
**Status:** Draft
**Last Updated:** July 2026

# 1. Purpose

This document defines how business events flow through the ScanServe platform.

It describes:

* Event producers
* Event consumers
* Business event lifecycles
* State transitions
* Real-time synchronization
* Backend responsibilities

The objective is to ensure that every business event follows a predictable, secure, and observable lifecycle.

---

# 2. Scope

This document defines:

* Business events
* Event ownership
* Event sequencing
* Firestore update flow
* Cloud Function responsibilities
* Client synchronization
* State transitions

This document intentionally excludes:

* Firestore document schemas
* API contracts
* UI implementation
* Repository implementation

---

# 3. Event Flow Principles

Every business event should follow these principles.

---

## 3.1 Single Event Source

Every business event has one authoritative source.

Examples:

* Customer submits Order
* Kitchen updates Order Status
* Manager publishes Menu

Business events must never originate from multiple sources simultaneously.

---

## 3.2 Predictable Flow

Every event follows the same lifecycle.

```text
Trigger
    ↓
Validation
    ↓
Business Logic
    ↓
Persistence
    ↓
Real-Time Synchronization
    ↓
Completion
```

---

## 3.3 Backend Authority

Business-critical events execute through trusted backend components.

Client applications initiate requests.

Backend components authorize and execute them.

---

## 3.4 Event Immutability

Historical business events should never be rewritten.

State changes generate new business states rather than modifying historical intent.

---

## 3.5 Observable State

Every significant business event should produce an observable state change.

This allows Flutter and Angular applications to synchronize through Firestore without polling.

---

# 4. Event Classification

Business events are grouped into four categories.

## Customer Events

Generated by customers.

Examples:

* QR scanned
* Cart updated
* Order submitted
* Waiter requested

---

## Staff Events

Generated by restaurant staff.

Examples:

* Order accepted
* Order prepared
* Order served
* Menu updated

---

## Platform Events

Generated automatically.

Examples:

* Session expired
* Notification dispatched
* Analytics collected
* Cleanup completed

---

## Administrative Events

Generated by restaurant managers.

Examples:

* Menu published
* Table created
* Staff invited
* Role assigned

---

# 5. Event Lifecycle

Every event progresses through the following lifecycle.

```text
Triggered
        ↓
Validated
        ↓
Authorized
        ↓
Executed
        ↓
Persisted
        ↓
Synchronized
        ↓
Completed
```

An event should never skip validation or authorization.

---

# 6. Event Ownership

Each event has one responsible owner.

| Event | Owner |
|--------|-------|
| QR Scan | Customer PWA |
| Customer Session Creation | Customer PWA |
| Cart Update | Customer PWA |
| Order Submission | Cloud Functions |
| Kitchen Status Update | Angular Dashboard |
| Menu Publication | Angular Dashboard |
| Session Cleanup | Cloud Functions |
| Notification Dispatch | Cloud Functions |

Ownership determines where business logic executes.

---

# 7. Real-Time Synchronization

Firestore provides real-time synchronization between platform components.

Applications should subscribe only to data required for their current workflow.

---

## Customer PWA

Listens to:

* Customer Session
* Cart
* Orders
* Table Session *(optional)*

---

## Angular Dashboard

Listens to:

* Active Orders
* Kitchen Queue
* Table Sessions
* Waiter Requests

---

## Cloud Functions

Respond to:

* Firestore document changes
* Scheduled events
* Callable requests

Cloud Functions should not maintain persistent application state.
